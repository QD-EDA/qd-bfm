# `smoke_test_mbox` first lock read trace

Slurm job 1614 ran a diagnostic-only build on DAN-DESKTOP with Verilator 5.052 (`v5.052`, SHA-256 `a2664fa7fa20cb9a4526567f9fc6217270080378b5138e97a74d54e939318287`). The instrumentation only printed AXI reads to the mailbox-lock CSR; it did not change handshake or return behavior. The upstream `axi_if.sv` SHA-256 was `e03bd7a7654eb9c31bd532861b94d59c876810aa9798f9f67f7df2a5a3f5495c`.

The focused run stopped at its separate 600-second diagnostic cap (`wrapper_exit=124`) and did not produce a terminal test result. The captured trace is still sufficient to identify the stall point: the first 12 mailbox-lock reads all completed their AR and R handshakes in one cycle, returned `RRESP=0`, and returned `RDATA=1`. The testbench never printed “Lock granted” or reached the command-register write. This is a completed AXI response carrying the locked value, not a missing AXI response.

The pinned mailbox-lock register is software-set-on-read (`mbox_csr.sv`, field update at lines 273–285); its readback uses the lock field (`mbox_csr.sv:664`). The SoC BFM reads that register in a `do/while` loop and repeats while bit 0 is one (`caliptra_top_tb_soc_bfm.sv:341–346`). The firmware has no earlier lock read in this flow: its only `MBOX_LOCK` read is at `smoke_test_mbox.c:109`, after the initial SoC mailbox exchange. The Verilator trace begins at the BFM’s first lock request. In contrast, the Icarus run reports that the lock was granted after one poll and completes the mailbox exchange.

The result mismatch is therefore rooted in the read-to-set lock handoff: Icarus sees the initially free value on the first poll, while Verilator returns `1` on that first read; the BFM then treats the lock as already held and polls forever. The exact simulator-versus-RTL scheduling cause of that differing read value is not isolated by this trace. The original M9 row remains `TIMEOUT`; this diagnostic is not a replacement row result.
