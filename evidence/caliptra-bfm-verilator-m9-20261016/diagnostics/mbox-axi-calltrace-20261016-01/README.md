# `smoke_test_mbox` lock poll call trace

Slurm job 1617 ran on DAN-DESKTOP with Verilator 5.052. It used pinned Caliptra RTL commit `49370266d12cb0c4a8f71b3a0ff7e54ba7d4866e` and QD-BFM source commit `857ee578b87c0c6d7ed9581914eb04c863bd3940` (source archive SHA-256 `afd6b8eff7f8868316904e1944f0b12f49eaf73d06e33934104f51b295768eb1`). The model changes only add prints around the mailbox-lock read and `axi_read_single`; the BFM loop, transaction timing, return arrays, and test logic are unchanged.

The 90-second diagnostic cap expired (`wrapper_exit=124`), so there is no terminal result JSON. The captured trace has 20 `SINGLE_BEGIN` and 20 matching `SINGLE_RETURN` events. Each read returned `data=1`, `resp=0`, `user=0`; every observed AR and R handshake completed in one cycle. No lock-granted message or `MBOX_CMD` write occurred before the cap. The instrumentation intentionally traces only the first 20 reads and every 1000th thereafter; it makes no claim about unlogged intermediate polls.

The pinned lock CSR is software-set-on-read (`mbox_csr.sv:273–285`, with reset value zero at line 289), and the SoC BFM repeats the read while returned bit 0 is one (`caliptra_top_tb_soc_bfm.sv:341–346`). The firmware's only lock-register read occurs later at `smoke_test_mbox.c:109`, after the initial SoC mailbox exchange. Thus the Verilator trace shows the SoC BFM's first acquisition read returning one; it then re-enters the same poll with the lock set. The original Icarus run grants the lock after one poll, meaning its first read returns zero, and completes the exchange.

This identifies the test-level cause of the Icarus-PASS versus Verilator-TIMEOUT: the read-to-set acquisition response is observed as `1` by Verilator, so the BFM mistakes its acquired lock for a busy lock and keeps polling. The trace does not determine whether the differing first-read value comes from Verilator scheduling or an upstream RTL race. The original M9 row remains `TIMEOUT`; this diagnostic is not a replacement result.
