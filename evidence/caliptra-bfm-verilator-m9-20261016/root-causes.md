# M8 carryover and M9 root-cause evidence

## M8 prior finding: `smoke_test_kv_lock_use_mid_read` expected status misclassified

The pinned Caliptra firmware treats a nonzero `error_field` as the expected result. It prints `[PASS]` for `error=0x1` and only reports failure when `error_field == 0`; the simulator exits 0 and emits `ALL CHECKS PASSED` plus `* TESTCASE PASSED`. The runner's case-insensitive `ERROR|FATAL` regex counts the lowercase `error=0x1` in both the result line and the PASS line, leaving `bad=2` and overriding the terminal PASS markers. This is a wrapper classifier bug, not a DUT or Verilator failure. The recorded M8 result remains FAIL under unchanged criteria. Filed as [QD-BFM #12](https://github.com/QD-EDA/qd-bfm/issues/12).

Evidence: [pinned upstream test source](https://github.com/chipsalliance/caliptra-rtl/blob/49370266d12cb0c4a8f71b3a0ff7e54ba7d4866e/src/integration/test_suites/smoke_test_kv_lock_use_mid_read/smoke_test_kv_lock_use_mid_read.c#L771-L804), [M8 result JSON](../caliptra-bfm-verilator-m8-20261015/verilator-timeout-tasks1372/task22_smoke_test_kv_lock_use_mid_read/results/smoke_test_kv_lock_use_mid_read/result.json), and [M8 simulator log](../caliptra-bfm-verilator-m8-20261015/verilator-timeout-tasks1372/task22_smoke_test_kv_lock_use_mid_read/results/smoke_test_kv_lock_use_mid_read/sim.log).

M9 task 1430_86 reproduces the same wrapper false positive: the log contains `* TESTCASE PASSED`, exits 0, and records `bad=2` because the expected `error=0x1` text appears twice. Its M9 table row therefore remains `FAIL` under the existing classifier; this is additional evidence for #12, not a new RTL or simulator failure. See [M9 result](runs/5623a0f9b5e00f77/result.json) and [M9 simulator log](runs/5623a0f9b5e00f77/sim.log).

## M9 required root cause: `jtag_tap_mbox` wrapper omits the required Tcl client

The firmware waits for `DATA_READY` after publishing its mailbox request. The suite's companion Tcl program is what drives the RISC-V DMI mailbox reads/writes, writes the terminal PASS byte, and shuts down. The existing full-top wrapper launches only the model with `+CLP_REGRESSION`; it never runs that Tcl client. Consequently the firmware remains in the mailbox wait, and the testbench's 20,000,000-cycle guard terminates the run after 11,181.286 seconds. The log has no testcase result or final mcycle. This is a wrapper coverage gap; the existing M8 result remains FAIL. Filed as [QD-BFM #13](https://github.com/QD-EDA/qd-bfm/issues/13).

Evidence: [pinned firmware](https://github.com/chipsalliance/caliptra-rtl/blob/49370266d12cb0c4a8f71b3a0ff7e54ba7d4866e/src/integration/test_suites/jtag_tap_mbox/jtag_tap_mbox.c), [pinned Tcl client](https://github.com/chipsalliance/caliptra-rtl/blob/49370266d12cb0c4a8f71b3a0ff7e54ba7d4866e/src/integration/test_suites/jtag_tap_mbox/jtag_tap_mbox.tcl), and [M8 simulator log](../caliptra-bfm-verilator-m8-20261015/verilator-timeout-tasks1372/task3_jtag_tap_mbox/results/jtag_tap_mbox/sim.log).

M9 array task 1430_149 reproduces the same 20,000,000-cycle guard failure under Verilator, with no final mcycle or firmware PASS marker. This confirms the issue #13 wrapper gap remains present in the M9 firmware flow; M9 row evidence is in [`runs/3439695c6637d6f2/`](runs/3439695c6637d6f2/).

## M9 required root cause: `cptra_ss_test_rom` reaches an unmapped AXI destination at FIFO word 15

The M9 row times out after 6,873 seconds with no testcase marker or final mcycle; c339 also has no terminal result, so this is not an Icarus-finished disagreement. The initial diagnostic stopped after the firmware reported space for FIFO word 15. The AXI trace then showed that word `0x67120ad3` was accepted with FIFO ready, and all 16 words drained. The DMA write to firmware destination `0x21200000` received `BRESP=11` (DECERR), set `AXIERR=1`, and moved the controller to `DMA_ERROR`. The firmware destination is outside the pinned testbench's two configured AXI windows, so this is a testbench memory-map mismatch, not a FIFO-full condition.

Diagnostic job 1769 added a logging-only `STATUS0` read probe at the verified offset `0x2200c`. All 18 sampled reads are in [`diagnostics/cptra-ss-dma-axi-20261016-04/raw/diagnostic-output/sim.log`](diagnostics/cptra-ss-dma-axi-20261016-04/raw/diagnostic-output/sim.log); the last, at the same simulation timestamp as the DMA error transition, reads `0x00010001` (busy=1, error=0). There are no later `STATUS0` reads, while the trace records 4,157 further reads of notification register `0x22818`, each followed by a W1C write of `0x1`, through the separate 600-second diagnostic cap.

The pinned firmware enables all DMA notification interrupts. Its notification ISR writes `NOTIF_TXN_DONE`'s W1C mask only when the status read contains that bit; the trace's repeated `0x1` clears therefore support repeated transaction-done notification service, although the monitor does not log read-return data. The RTL asserts `notif_txn_done_sts.hwset` throughout `DMA_DONE` or `DMA_ERROR`, and generated CSR logic gives that hardware set priority over the software W1C. `DMA_ERROR` remains active until firmware writes `CTRL_FLUSH`, so the notification stays asserted across the ISR clears. The wait helper would read `STATUS0` and flush after observing the error, but the trace instead shows repeated notification service and no later status poll. Together, the RTL/firmware paths and trace strongly support a reasserting DMA notification interrupt preventing the mainline wait/flush path from progressing. The trace does not include the CPU PC or notification-register readback, so that last step is a source-backed inference, not a direct processor trace.

The root cause is the missing `0x21200000` target in the top-testbench AXI map, with the persistent notification interrupt explaining why the observed DECERR becomes a timeout. No simulator defect is indicated and no issue was filed. Diagnostic jobs 1606, 1763, and 1769 are separate probes; none replaces or changes the official M9 row.

## M9 required root cause: Verilator's read-to-set lock response traps `smoke_test_mbox` in its poll

The Icarus c339 run passes at mcycle 74,924; its SoC BFM reports that it received the mailbox lock after one poll, writes the command and data, completes the exchange, and prints `* TESTCASE PASSED`. The pinned Verilator 5.052 row reaches the same first mailbox-lock handoff, then times out before lock grant or the command write. Both runs use the same firmware image hashes recorded in [`disagreements.md`](disagreements.md).

The pinned mailbox-lock CSR is software-set-on-read: `mbox_csr.sv` sets the lock when a read is decoded (lines 273–285), resets it to zero (line 289), and reads back the lock field (line 664). The SoC BFM polls until the returned lock bit is zero (`caliptra_top_tb_soc_bfm.sv:341–346`). The firmware's only lock read is later in `smoke_test_mbox.c:109`, after the initial SoC exchange; before then it waits for mailbox status. The BFM therefore makes the first lock read in this handoff.

Diagnostic job 1614 showed completed AR/R handshakes returning `RDATA=1`, not an unanswered AXI read. Job 1617 added markers around `axi_read_single` and captured 20 consecutive lock reads: all 20 tasks returned `data=1`, `resp=0`, then the BFM began the next poll. The 20 `SINGLE_BEGIN` markers pair with 20 `SINGLE_RETURN` markers, and each logged read has one completed AR/R handshake; no extra or reordered read appears in the traced calls. It never logged lock grant or the command-register write before its separate 90-second diagnostic cap. The BFM therefore treats the first acquisition read as busy; that read sets the lock, and each subsequent read continues to observe it as set. The Icarus run reports a one-poll grant and completes the exchange, so its first read sees the free value (`0`). This roots the result disagreement in the lock's read-to-set response and the BFM's polling condition, rather than AXI response delivery. The trace does not determine whether Verilator scheduling or an upstream RTL race causes the first-read value difference.
